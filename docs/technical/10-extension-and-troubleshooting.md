# 10 扩展流程、故障排查与维护边界

[返回目录](README.md)

## 1. 新增一个普通法术的完整路径

下面是维护步骤，不是能直接复制编译的通用插件 API。当前机制有枚举和多个 switch，新增一项并不会自动生成完整玩法。

### 定义与注册

在 `Spell` 末尾追加枚举，不重排现有 ordinal。填写独立费用、范围、生命周期、基色，并检查是否属于 projectile、rolling、evolved/base。注册循环会产生旧卡物品，但对应资源不会凭空生成。

在 `IronSpellProfile` 添加同名 profile，确定学派、稀有度、等级上限、魔力、吟唱和冷却，补 powerPerLevel/duration 等有必要的分支。只走特殊原生路线的法术可像军团一样不对应 `Spell`，但必须处理 `card()==null` 的预览、图标和 onCast 分支。

### 服务端行为

在 `SpellEntity` 对应 field/projectile/roll 中实现明确的 tick 时序。逻辑应只在服务端跑，重复命中需 hit 集合或显式跳数，不用粒子数量决定伤害。

通过 `IronSpellSystem.damage/heal/summon` 保留原生接入，指定真实目标和法术来源。无原作明确位移的伤害不附加推力；需要位移时调用 `SpellMotion`，兼顾 NoAI 与碰撞。

确定持续状态是只作用于初始锁定目标，还是持续查询进入区域的新目标。两种规则差别很大：藤蔓初始锁三人，冰冻每 tick 查区域。

### 预览与视觉

半径检查 `Spell`、服务端硬编码、`TargetPreview`、视觉覆盖。特殊形状需增加 `TargetGeometry` 和当前手持识别，不要恢复逐顶点贴地。

选择使用实体模型、领域几何还是粒子；确定绘制阶段与局部坐标。半透明覆盖层用只写颜色的 RenderType。为展开、循环、命中和结束分别设计动画，并使用同步时间和目标点，避免客户端随机效果决定机制。

### 资源、音频与取得方式

添加卡图、物品模型、铁魔法 GUI 图标、中英文语言键和必要粒子 JSON。原卡图的原始比例、来源和哈希应记录。

添加实际需要的音效阶段至 `spell_audio.json` 和 `sounds.json`，确认事件存在、OGG 格式、传播范围和单次触发。每个 `Spell` 至少有 deploy，否则启动检查会失败。

添加无铁魔法时旧卡牌配方，带正确 NeoForge 条件；铁魔法默认可制作与稀有度/媒介规则从 profile 接入。仪式专属法术应主动关闭普通制作和战利品，而不是仅在说明写“稀有”。

### 验证与文档

覆盖实际原生施法入口、失败条件、范围边界、伤害跳数、取消、克隆/镜像、NBT 和无依赖启动。视觉检查近远、不同角度、实体遮挡、手持切换和材质。更新新档案，运行生成器与链接检查。

## 3. 按症状定位

| 症状 | 入口与证据 |
| --- | --- |
| 游戏启动即 Mixin 错误 | 首个 Caused by、目标类/方法、当前 JAR、铁魔法与 GeckoLib 版本；查 08 |
| 没铁魔法就崩溃 | 公共签名是否提前加载上游类型、@Pseudo 与插件过滤、compileOnly / runtime 区分 |
| 法术没出现在制作列表 | 当前学派、稀有度、启用、allowCrafting、学习条件、材料 grade 和候选缓存 |
| 投放卷轴不触发仪式 | 必须原生 Scroll、正确法术 ID、natural 源、Y 位置、周围无仪式、无 grace |
| 号角不召唤 | 自定义组件、铁魔法启用、正在吟唱、军团有效期、CD、16 点空间 |
| 预览随视角漂移 | 相机矩阵叠加、世界/局部坐标混用、delta 不一致 |
| 预览在树上拉长 | 逐顶点地形采样导致不共面；查几何不变量 |
| 透明领域遮断人物 | COLOR_WRITE 与实际深度缓存前后对比 |
| NoAI 目标不被推拉 | 不能只设置 velocity；检查 SpellMotion 移动路径与建筑锚定 |
| 生物不动但还摆手 | 只有服务端 STUN，没有客户端骨骼 Scope；检查渲染库是否被覆盖 |
| 部队见和平生物就打 | SummonOrders 是否执行、主人是否正确、目标事件是否被别的监听器覆盖 |
| 野蛮人剑嵌进胳膊 | translateToHand 的父骨骼、掌心偏移、原生手持层半转 |
| 近处吵、远处无声 | 声道、sounds.json attenuation_distance、固定事件范围、实际音量分类 |
| 大闪只响一声 | 声音是否绑在统一 deploy 而非 2/8/14 的真实目标 |
| 地震重启后裂纹消失 | 当前共享裂纹表是运行时数据，不是永久破坏进度 |
| 改源码游戏没变化 | 当前实例是否仍加载旧 JAR、重复 JAR、源码分支与安装目标是否一致 |

判断渲染性能先查日志实际 OpenGL Renderer、分辨率、光影与模组组合。不能从卡顿程度直接认定是某张显卡或某个法术；本档案不把机器专用设置写成模组修复流程。

## 4. 性能与数量限制

| 区域 | 当前措施 | 剩余成本 |
| --- | --- | --- |
| 预览 | 单玩家每帧有限轮廓，不创建实体 | 每帧目标射线和几何分配 |
| 领域/覆盖 | 96 格距离筛选 | 每帧遍历可渲染实体与透明填充 |
| Zap | 同步最多 16 点、绘制最多 8 个目标分支 | CompoundTag 更新与多层电弧 |
| 普通召唤 | 每主人 64 / 当前维度 256 | 每次召唤扫描当前实体集合 |
| 军团 | 每玩家一支 16 人，有限寿命 | 多玩家和中立实验蛋没有同一套全局部署数量预算 |
| 地震 | 2048 候选、128/每 tick、8192 裂纹 | 建筑较多时持续查询和客户端裂纹广播 |
| AI | 每 5 tick 调目标 | 扫描、可见性和第三方 AI 开销 |
| 冻结姿势 | 每实体弱引用缓存 | 骨骼数量多的模型仍有缓存/包装成本 |
| 深度审计 | 仅显式测试开启 | 全屏 GPU→CPU 读取，不能常驻 |

性能优化应先测具体场景，不能为了减少代码行数删除条件、finally 或每实体隔离。可改进方向包括复用轮廓缓冲、增加缓存失效处理、减少同一 tick 重复扫描，但这些只是后续工作，不在当前版本中假装已经实现。

## 5. 已知实现边界

- 多个法术范围仍在服务端硬编码；新增数据驱动范围系统需要统一机制与视觉。
- 独立卡牌和原生法术并非所有行为一致，尤其镜像、受伤间隔、英雄再施放与自我瞄准。
- 预览不是有效性检测，不表现魔力/CD、全部权限、军团/建筑完整碰撞。
- 当前 GUI 适配依赖上游 UV 和 blit 顺序；不同版本、资源包或第三方界面替换需复测。
- 源码中有旧制作脚本、未常用渲染器和开发检查类，完整索引只说明它们存在，不表示每个都在正常游戏执行。
- 军团、仪式的保存支持不等于所有中间动画/极端事件取消都拥有事务式恢复。
- 生成池概率命中也可能因为地形不合适而跳过，旧塔不自动更新。
- 客户端源码检查和固定组合测试不等于所有多人、Boss、第三方技能与光影兼容保证。

## 6. 接手者第一轮审查

确认分支、版本、依赖与源码基线 → 运行文档检查与构建 → 分开验证独立/同装 → 重现一个简单法术 → 用真实输入检查一个卷轴和一个镜像 → 再进入需要修改的专题。一次保留小而明确的改动，并在同一提交更新说明和相关证据。

发现本档案和源码不一致时，先记录具体 ID、类、方法和基线，不要用旧说明覆盖当前代码。没有跑过的验证写“未执行”，观察到但未定位的问题写“待定位”，不要为了让技术档案看起来完整而补写未经验证的能力。
